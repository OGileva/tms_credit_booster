# TMS Credit Booster

Проект для хранения тест-кейсов в Git. Кейсы хранятся в Markdown, а CLI помогает импортировать таблицы, искать нужные проверки, проверять каталог и делать выгрузки.

## Быстрый старт

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
qa-cases validate
```

Обычный рабочий порядок:

1. посмотреть разделы командой `qa-cases sections`;
2. проверить входной файл и выполнить импорт с `--dry-run`;
3. повторить импорт без `--dry-run`;
4. проверить результат командами `qa-cases validate` и `make test`;
5. найти или выгрузить нужные кейсы через `qa-cases list` или `qa-cases export`.

## Хранение

- `cases/` — групповые Markdown-файлы тест-кейсов, каждый блок содержит TOML front matter.
- `dictionaries/tags.json` — допустимые теги и русские aliases.
- `exports/` — локальные выгрузки, не коммитятся.
- `id-registry.json` — журнал выданных ID; нужен, чтобы удалённые номера не переиспользовались.

Кейсы одной части модуля хранятся группой в одном Markdown-файле. Имя группы строится по первому и последнему разделу пути: `листинг/клиенты` → `листинг клиенты.md`; для цепочки из нескольких разделов берутся крайние элементы.

В `Description` кейса можно добавить относительную ссылку на документ из `docs/`; это необязательное пояснение. Обязательные поля тест-кейса: `Name` (Название), `Preconditions` (Предусловия), `Steps` (Шаги воспроизведения), `Expected Result` (Ожидаемый результат). Опциональные поля: `Description` (Описание), `Tag`/`Tags` (Тег), `Criticality` (Критичность: `critical`, `medium` или `low`). ID кейса — только число от 1 до 999999, без ведущих нулей и префикса.

Функционал задаётся папкой и `section.json`. Канонические теги хранятся на русском: `регресс` включает кейс в регресс, `смоук` — в набор smoke, `критичный` обозначает принадлежность к набору критичных кейсов. Например, `tags = ["критичный", "регресс"]` означает критичный регрессионный кейс. Отдельное поле `criticality` принимает `critical`, `medium` или `low`.

## Настройка

Из корня репозитория:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
qa-cases validate
```

Зависимости объявлены в `pyproject.toml`. `project.json` служит маркером корня каталога. Без активации окружения команды можно запускать как `.venv/bin/python -m qa_cases ...`.

Корень репозитория открывается в AI-редакторе. Codex использует `AGENTS.md`, Claude Code — `CLAUDE.md`, Cursor — `.cursor/rules/test-cases.mdc`. Эти файлы описывают правила работы, но сами тест-кейсы находятся только в `cases/`.

## Добавление документации
 
Пример запроса агенту:

> Добавь описание функционала «Тестовый раздел» в docs/credit-booster/demo/sample-section.md и ссылку на него в оглавление docs/README.md.

Документация редактируется как обычный Markdown. CLI предназначен для тест-кейсов; отдельного поиска или экспорта документации в нём нет.

## Добавление кейсов

Сначала посмотреть существующие разделы:

```bash
qa-cases sections
```

Если нужного раздела нет, создать его. Пример:

```bash
qa-cases create-section --product credit-booster --path demo/sample-section --name "Тестовый раздел" --id-prefix CB-DEMO --alias "Пример раздела"
```

Пример запроса агенту:

> Добавь кейсы из приложенного файла в продукт Credit Booster, раздел «Тестовый раздел». Добавь тег «регресс» и связь с CBN-1234. Не коммить.

Эквивалентная CLI-команда:

```bash
qa-cases import --source /path/to/cases.xlsx --product credit-booster --section "Тестовый раздел" --tag регресс --task CBN-1234 --dry-run
```

После проверки повторить без `--dry-run`. Импорт поддерживает XLSX, CSV/TSV, JSON, DOCX и Markdown-таблицы. Шаблоны находятся в `_templates/`. Если в строке нет обязательного поля или указан неизвестный тег, импорт останавливается без записи неполного набора.

До записи кейсов проверяется весь входной файл. Ошибка в непустом листе XLSX или таблице DOCX останавливает весь импорт. Пустые листы и таблицы пропускаются; непустые справочные листы и таблицы следует убрать из входного файла.

Перед записью импорт проверяет дубли по обязательным полям `Name`, `Preconditions`, `Steps`, `Expected Result`. Полностью совпадающий кейс не импортируется; его теги, описание и критичность не создают новую запись. Проверка выполняется и против уже сохранённых кейсов, и внутри одного входного файла.

ID из входного файла не используется: колонку `ID` можно не передавать, а если она есть, её значение игнорируется. После импорта ID назначаются автоматически по порядку как числа `1` … `999999`, без ведущих нулей и префикса. Новое значение берётся после максимального уже существующего номера; удалённые ID не переиспользуются.

Новый тег сначала добавляется в `dictionaries/tags.json` с описанием и при необходимости русскими aliases. Критичность задаётся отдельным полем `criticality`; для набора критичных кейсов дополнительно используется тег `критичный`.

## Выборка и выгрузка

Примеры запросов агенту:

> Покажи только регрессионные кейсы раздела «Тестовый раздел».

> Выгрузи все критичные кейсы в Excel вместе с тегами и статусом.

> Выгрузи только критичные регрессионные кейсы в JSON.

Эквивалентные команды:

```bash
qa-cases export --section "Тестовый раздел" --tag регресс
qa-cases export --tag критичный --format xlsx --include-metadata
qa-cases export --tag регресс --tag критичный --format json
```

Без указания формата возвращается Markdown-таблица. Файлы сохраняются в `exports/`; свой путь задаётся через `--output exports/selection.xlsx`. Команда `list` только показывает найденные кейсы, а `export` создаёт файл.

| Формат | Содержимое |
|---|---|
| XLSX, CSV, Markdown, таблица в чате | Колонки Name, Description, Preconditions, Steps, Expected Result; ID включён в Name |
| Те же форматы с `--include-metadata` | Дополнительно ID, Tags, Status, Tasks, Criticality |
| JSON | Все поля кейса и метаданные, независимо от флага |

CLI поддерживает экспорт в XLSX, CSV, JSON и Markdown. PDF, DOCX и другие форматы требуют отдельного преобразования агентом, если доступен подходящий инструмент; встроенной поддержки их экспорта пока нет.

Фильтры `--product`, `--section`, `--tag`, `--id`, `--search`, `--status` можно комбинировать. Несколько тегов означают **И**: регресс и критичные. По умолчанию выбираются только `active`; `--status draft`, `--status deprecated` или `--status all` меняют выборку. Отбор по задаче доступен через `--search CBN-1234` как поиск подстроки.

Русские aliases тегов и разделов разрешаются автоматически. При неоднозначном названии раздела нужно указать `--product`. Для выборки поддерживаются glob-шаблоны путей, например `--section 'demo/*'`.

## Команды

| Команда | Назначение |
|---|---|
| `qa-cases sections` | Продукты, разделы, aliases и префиксы ID |
| `qa-cases create-section ...` | Создать функциональный раздел |
| `qa-cases import ...` | Массово добавить кейсы |
| `qa-cases list ...` | Краткий список с ID и тегами |
| `qa-cases export ...` | Выгрузить выборку |
| `qa-cases validate` | Проверить каталог |

## Разработка и review

`qa_cases/` содержит CLI, `schemas/` — схемы метаданных, `tests/` — проверки инструмента. Валидация проверяет обязательные поля, ID, структуру разделов, теги, уникальность названий и нумерацию списков. Соответствие ожидаемых результатов требованиям проверяется при review.

Перед передачей изменений:

```bash
make check test
git diff --check
git status --short
```

`make` использует `.venv`, если окружение создано. Другой интерпретатор: `make PYTHON=/path/to/python check test`.

Порядок review и коммита — в [CONTRIBUTING.md](CONTRIBUTING.md). Commit и push выполняются только по прямому запросу QA.
